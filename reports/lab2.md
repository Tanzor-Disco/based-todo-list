# Лабораторная работа № 2
# Контейнеризация приложения с использованием Docker

## 1. Цель работы

Контейнеризировать разработанное ранее веб-приложение с использованием Docker и Docker Compose. Изучить влияние структуры Dockerfile на размер итогового образа, безопасность запуска приложения, эффективность кеширования при повторной сборке и организацию взаимодействия сервисов.

## 2. Используемые технологии

- Docker и Docker Compose
- Go
- PostgreSQL
- Alpine Linux
- golang-migrate

## 3. Хороший Dockerfile

Для контейнеризации backend используется многоэтапная сборка (multi-stage build). На первом этапе в образе `golang:1.26.4` загружаются зависимости и компилируется приложение. На втором этапе используется `alpine:3.22`, куда копируется только исполняемый файл.

### 3.1. Содержимое Dockerfile

```dockerfile
FROM golang:1.26.4 AS builder

WORKDIR /app

COPY go.mod go.sum .
RUN go mod download

COPY . .
RUN CGO_ENABLED=0 go build -o todo-backend .

FROM alpine:3.22

RUN addgroup -S appgroup && adduser -S appuser -G appgroup

WORKDIR /app

COPY --from=builder /app/todo-backend .

USER appuser

CMD ["./todo-backend"]
```

### 3.2. Использованные практики

**Многоэтапная сборка.** Этап компиляции отделён от этапа запуска. Компилятор Go и инструменты сборки не включаются в итоговый образ, что уменьшает его размер.

**Фиксированные версии образов.** Используются `golang:1.26.4` и `alpine:3.22` вместо `latest`, что делает выбор базовых образов более предсказуемым.

**Кеширование зависимостей.** Файлы `go.mod` и `go.sum` копируются отдельно от исходного кода. Если зависимости не меняются, Docker может повторно использовать слой с результатами `go mod download`.

**Отключение CGO.** Параметр `CGO_ENABLED=0` используется при компиляции. Полученный бинарный файл корректно запускается в используемом runtime-образе.

**Непривилегированный пользователь.** Создаётся пользователь `appuser`, от имени которого запускается приложение. Это соответствует принципу минимальных привилегий.

**Файл `.dockerignore`.** Исключает ненужные файлы из контекста сборки.

## 4. Плохой Dockerfile

Для сравнения подготовлен Dockerfile с намеренно допущенными недостатками.

### 4.1. Содержимое Dockerfile.bad

```dockerfile
FROM golang:latest

WORKDIR /app

COPY . .

RUN go mod download
RUN go build -o todo-backend .

EXPOSE 8080

CMD ["./todo-backend"]
```

### 4.2. Плохие практики

**Использование `latest`.** Конкретная версия базового образа не зафиксирована, поэтому при последующих сборках может использоваться другая версия образа, снижая воспроизводимость.

**Отсутствие multi-stage build.** Итоговый образ содержит компилятор Go и инструменты разработки, которые не требуются для запуска приложения.

**Неэффективное кеширование.** Сначала копируется весь проект, а затем загружаются зависимости. При изменении исходного кода слой копирования меняется, что может привести к повторному выполнению последующих инструкций.

**Запуск от имени root.** Директива `USER` отсутствует, поэтому приложение запускается от имени пользователя по умолчанию, которым в данном образе является `root`.

**Отсутствие HEALTHCHECK в Dockerfile.** В самом образе не задана проверка состояния приложения. В хорошей конфигурации проверка backend задаётся через Docker Compose.

## 5. Сравнение размеров Docker-образов

Для сравнения были собраны два образа: `todo-good` и `todo-bad`. Их размеры получены с помощью команды `docker images`.

| Показатель | Хороший образ | Плохой образ |
|---|---:|---:|
| Content Size | 13,1 МБ | 374 МБ |
| Disk Usage | 39,7 МБ | 1,6 ГБ |

По показателю Content Size плохой образ примерно в 28,5 раза больше хорошего.

Это объясняется многоэтапной сборкой: в хорошем образе остаются исполняемый файл и окружение для запуска, а в плохом варианте сохраняются компилятор и инструменты разработки.

Таким образом, в проведённом эксперименте многоэтапная сборка позволила существенно уменьшить размер итогового образа.

## 6. Сравнение времени пересборки

Сначала было измерено время сборки без изменений исходного кода. Затем в Go-файл была добавлена одна строка-комментарий, после чего сборка была повторена. Измерения выполнялись командой `time docker build`.

| Сценарий | Хороший Dockerfile | Плохой Dockerfile |
|---|---:|---:|
| Без изменений исходного кода | 1,851 с | 0,638 с |
| После изменения исходного кода | 10,999 с | 19,128 с |

После изменения исходного кода хороший вариант собрался примерно в 1,74 раза быстрее плохого.

В хорошем Dockerfile зависимости загружаются до копирования исходного кода, поэтому изменение исходного файла не требует повторного выполнения `go mod download`, если `go.mod` и `go.sum` остались прежними.

В плохом Dockerfile сначала копируется весь проект, поэтому изменение исходного файла инвалидирует слой копирования и может привести к повторному выполнению загрузки зависимостей.

При сборке без изменений исходников плохой вариант оказался быстрее. Результат зависит от состояния кеша и условий выполнения. В эксперименте после изменения исходного кода преимущество получил хороший Dockerfile.

Результат:

Проверка подтвердила, что приложение запускается от имени пользователя `appuser`, а не `root`. Это снижает потенциальные последствия компрометации приложения за счёт ограничения его привилегий.

## 8. Docker Compose

Для запуска приложения используется Docker Compose. В текущей архитектуре определены два сервиса: `backend` и `postgres`. Frontend собран и раздаётся Go backend в виде статических файлов.

### 8.1. Хорошая конфигурация compose.yaml

```yaml
services:
  backend:
    build: ./backend
    env_file:
      - ./.env
    ports:
      - "80:8080"
    depends_on:
      postgres:
        condition: "service_healthy"
    healthcheck:
      test: ["CMD", "wget", "-q", "--spider", "http://127.0.0.1:8080/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s

  postgres:
    image: postgres:18
    env_file:
      - ./.env
    volumes:
      - postgres_data:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U \"$${POSTGRES_USER}\" -d \"$${POSTGRES_DB}\""]
      interval: 5s
      timeout: 5s
      retries: 5

volumes:
  postgres_data:
```

### 8.2. Использованные практики

- **Именованный том `postgres_data`.** Данные PostgreSQL хранятся отдельно от контейнера и сохраняются при его пересоздании, пока том не удалён.
- **Healthcheck PostgreSQL.** Команда `pg_isready` проверяет готовность сервера базы данных принимать подключения.
- **Healthcheck backend.** HTTP-проверка обращается к эндпоинту `/health`.
- **Ожидание готовности БД.** Условие `service_healthy` учитывает готовность базы данных при запуске backend.
- **Отсутствие опубликованного порта PostgreSQL.** Backend взаимодействует с базой данных через внутреннюю сеть Docker Compose.

Healthcheck сообщает о состоянии сервиса, но сам по себе не гарантирует автоматический перезапуск контейнера.

### 8.3. Плохая конфигурация compose.bad.yaml

```yaml
services:
  backend:
    build:
      context: ./backend
      dockerfile: Dockerfile.bad
    env_file:
      - ./.env
    ports:
      - "80:8080"
    restart: always

  postgres:
    image: postgres:latest
    env_file:
      - ./.env
    ports:
      - "5432:5432"
    restart: always
```

В плохой конфигурации используется `postgres:latest`, отсутствует именованный том для базы данных, а порт PostgreSQL опубликован на хост. Также не настроены healthcheck-проверки и зависимость backend от готовности БД.

Политика `restart: always` не заменяет проверку состояния сервисов.

### 8.4. Сравнение конфигураций Compose

| Критерий | Хорошая конфигурация | Плохая конфигурация |
|---|---|---|
| Образ PostgreSQL | `postgres:18` | `postgres:latest` |
| Сохранение данных | Именованный том | Том отсутствует |
| Публикация порта БД | Не публикуется | `5432:5432` |
| Проверка готовности БД | `pg_isready` | Отсутствует |
| Проверка backend | `/health` | Отсутствует |
| Зависимость от готовности БД | `service_healthy` | Не настроена |

### 10. Сохранение данных PostgreSQL

Для хранения данных PostgreSQL используется именованный том `postgres_data`, подключённый к каталогу данных базы. Благодаря этому данные хранятся отдельно от жизненного цикла контейнера.

Для проверки сохранности данных контейнеры были остановлены и запущены повторно с помощью команд:

```bash
docker compose down
docker compose up -d
```

При остановке контейнеров именованный том не удалялся. После повторного запуска приложения сохранённая пользовательская сессия продолжила работать: приложение автоматически перенаправило пользователя на главную страницу.

Это подтверждает сохранение состояния приложения после пересоздания контейнеров и согласуется с тем, что данные PostgreSQL хранятся в именованном томе, а не только внутри контейнера.
## 11. Сетевая организация

Frontend приложения встроен в Go backend и не является отдельным сетевым сервисом. Backend взаимодействует с PostgreSQL через внутреннюю сеть Docker Compose. Порт PostgreSQL не опубликован на хост, поэтому подключение к базе через опубликованный порт извне не предусмотрено.

## 12. Вывод

В ходе лабораторной работы были разработаны хороший и плохой варианты Dockerfile и конфигурации Docker Compose.

Эксперимент показал, что многоэтапная сборка существенно уменьшает размер итогового образа. После изменения исходного кода хороший Dockerfile также показал меньшее время пересборки благодаря более эффективному кешированию зависимостей.

Проверка `whoami` подтвердила, что backend запускается от имени непривилегированного пользователя `appuser`. В хорошей конфигурации Compose предусмотрены healthcheck-проверки, ожидание готовности PostgreSQL и именованный том для хранения данных. Публикация порта базы данных не требуется для взаимодействия backend с PostgreSQL внутри сети Compose.
